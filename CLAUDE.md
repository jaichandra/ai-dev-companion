# CLAUDE.md

Guidance for Claude Code when working in this repository.

## What this is

`ai-dev-companion`: the generic framework behind a Chrome extension plus a local Node "companion service" that add one-click AI actions to git-host, issue-tracker and CI pages. It has no knowledge of any one organization: a **distribution** (a separate repo) supplies an environment profile and optional packs, and `scripts/assemble.js` merges the two into the tree that runs. See `README.md`.

## Commands

Run from `companion-service/` (Node >= 22.13):

- `npm install`, `npm run build` (`tsc -p .` into `dist/`; `.js` and `.ts` compile together, tests excluded), `npm test`.
- `npm run test:example` (repo root) assembles this repo with `examples/minimal-env` (a GitHub profile) and runs its test. `npm test` runs `node --test` over an **explicit file list in `package.json`**. A new `*.test.js` is not run until you add it there. Many tests load `dist/`, so build first.
- Single test: `node --test core/settings.test.js`.
- `npm run setup` (wizard), `npm run doctor`, `npm run service:install|uninstall|status`; CLI `bin/companion.js`.

This repo's own tests run against its placeholder profile (`companion-service/environment.js`, `example.com` hosts, builtin pack only). Tests that need a distribution's values belong in that distribution.

## Architecture

- `chrome-extension/` — one file per feature in `features/`, each calling `PaiRegistry.register(entry)` (`registry.js` documents the entry contract: `site` kind, `urlPattern`, `condition`, `settingsGroups`, `describePendingStart`, …). `content.js` renders the ✨ button and the overlay panel; `background.js` is the service worker; `settings-panel.js` is the Settings UI. `manifest.json` is generated by `companion-service/core/extension-manifest.js` (hosts from the profile's sites and `config.json` base URLs, scripts from the packs) and rewritten by `setup.js`; `doctor` checks it.
- `companion-service/server.ts` — Express app: feature routes, background/scheduler routes, `POST /mcp`.
- `companion-service/environment.js` — the placeholder profile; `core/environment-base.js` (`defineEnvironment`) validates one. Code reads the profile through its helpers and never hardcodes a host, job name or model.
- `companion-service/core/packs.js` + `packs/builtin.js` — packs list features; each feature has `features/<id>/feature.js` (plain JS so `setup.js` can require it without a build) and `index.ts`. The registry, `server.ts`, MCP catalog, scope keys, job persistence and history rules all read from the loaded packs.
- `companion-service/core/providers.ts` — `GitHost`, `IssueTracker`, `CiServer` interfaces; implementations: git host Bitbucket DC (`bitbucket*.js/ts`) or GitHub (`github.ts`, `github-endpoints.js`, `github-normalize.js`: REST + GraphQL, token-only), Jira DC, Jenkins. Features use `deps.providers`. Which one is the profile's git site (`sites[].provider`).
- Git-host differences live in `core/prereqs.js` `GIT_REMOTE_RULES` (origin parsing, clone URLs, PR page paths, PR keys `bitbucket:PROJ/repo#n` / `github:owner/repo#n`) and in `chrome-extension/git-host.js` (`PaiGit`: PR page pattern, scope key, how the PR is read). A site may be `tokenOnly` (no browser login: left out of host permissions and session relay) and may narrow the extension with `pageMatches`.
- `GET /prs/status` (`core/pr-status.js`) answers the extension's questions about the PR on a page through the git provider, cached for seconds; the GitHub path of the extension uses it instead of calling the API itself.
- `core/` also holds the Claude runner and guards (`claude*.js`, `*-guard`, `*-policy`), jobs, history, scheduler, settings, credentials, MCP, updater.
- Many `core/*.js` files are intentionally plain JS (no build step) because `setup.js`, `doctor.js` and the CLI require them directly.

## Design decisions to respect

- Conflict resolution merges the target branch in (never rebases) so the push is a plain, non-force `git push`. Approve & Push refuses if the worktree fingerprint differs from what the panel rendered.
- Claude jobs run in disposable worktrees, never the user's working copy; analysis is read-only.
- Keep organization-specific names (hosts, job names, internal tools) out of this repo; they belong in a distribution's profile or pack.

## Docs

`docs/DESIGN.md` (~2,600 lines) is the design: read the relevant section before changing a subsystem. It is written against the placeholder profile; keep organization-specific facts (hosts, internal tools, instance versions that only one deployment has) in the distribution's own docs.

## Tool output

Keep output small: run tests quiet and show failures only; use ranged reads for big files.
